## このリポジトリが検査すること

このリポジトリは、小さなUVMテストと実行用スクリプトを提供します。シミュレータはSystemVerilog言語を実行し、UVMライブラリはテストが使う検証用クラスを提供します。kirimasim-testsとの役割の境界は[検査の対象](testing.ja.md#確かめること)にあります。

期待値は引用した規格から定めます。Accelleraライブラリは、固定情報ファイル（uvm.lock）で版と内容を指定した、実際に検査する実装です。不一致の原因にはシミュレータ、ライブラリ、テストがあり得ます。[期待値の出典](provenance.ja.md#ライブラリと規格)を参照してください。

テストの`u09`などのディレクトリは最初のUVM条項引用に従うため、ソースを探す際の章・付録の名前は[配置の案内](testing.ja.md#ディレクトリ構成)で確認できます。

9.8.1などの引用は指定した規格内の場所、ファイル名末尾の`_109`などは追加作業のまとまりを示す番号で、規則とテストの追加時点の違いは[メタデータの項目](testing.ja.md#メタデータ)と[開発履歴](history.ja.md)で確認できます。

各テストの冒頭には、引用する規則や期待出力を記録したメタデータがあり、ソース内での場所は[ヘッダーの例](testing.ja.md#例)で確認できます。

ソースのオブジェクト参照、型パラメーター、フックは検査系がUVMを使う仕組みを表し、観測を辿る前に[コード表記の用語](glossary.ja.md#コードの表記を読む)で読み方を確認できます。

レジスタのテストの多くは、独自のテストベンチ内の記憶域を使います。frontdoor／backdoorという語だけでは実際のHDLへのアクセスを示さないので、[レジスタモデルの用語](glossary.ja.md#レジスタモデル)と[別のHDLアクセス用実装](testing.ja.md#verilatorのvpi-hdl部分集合)で区別を確認してください。

## 最初の実行の前に

ソースのパスは検査系を選び、`+UVM_TESTNAME=t`はその中で登録されたUVMテストクラスを選ぶ指定で、[ヘッダーの例](testing.ja.md#例)では両方の名前を確認できます。

Python 3.10以降、Verilator 5.052、C++コンパイラなどのビルド環境、makeを用意します。READMEのある最上位ディレクトリ（リポジトリのroot）から、[FAQ Q3](faq.ja.md#q3-まず1件だけ動かすにはどうしますか)の動作確認用コマンドを実行してください。VerilatorはC++のモデルを生成するため、そのビルドにC++コンパイラとmakeを使います。UVM取得コマンドは固定ライブラリをダウンロードし、シミュレータ自体のインストールは行いません。

明示したテストのパスは1ケースを選びます。seed 1と73は、同じビルド済みモデルを乱数の初期値を変えて別プロセスで実行する指定です。全件へ広げる前に[実行スクリプトのオプション](testing.ja.md#スイートの実行)を確認してください。

コマンドを開始できなければ、実行ファイルの版とビルド用ツールを[必要な環境](faq.ja.md#q2-必要な環境とuvmの取得元は何ですか)と照合してください。実行できて差分を報告した場合は、次の結果の説明を使います。

## 実行条件を選ぶ

runnerはビルドと実行の環境を供給するため、検査系のbackendメタデータに合わせて選び、指定の読み方は[メタデータのガイド](testing.ja.md#メタデータ)で確認できます。

- 最初の動作確認や通常のUVMケースは、HDL用・command-line用backendをlinkしない[通常runner](testing.ja.md#スイートの実行)を使います。
- `:uvm_hdl_backend: vpi`を宣言する検査系は、選択したUVM呼び出しを実際のシミュレータ内の記憶域につなぐ[HDL runner](testing.ja.md#verilatorのvpi-hdl部分集合)を使います。
- `:uvm_cmdline_backend: vpi`を宣言する検査系は、実際のprocess引数とregex対応を供給する[command-line runner](testing.ja.md#verilatorのcommand-line部分集合)を使います。

同じ入力でもこの環境の違いで結果が変わるため、[実測範囲](results.ja.md#現在のスナップショット)の対応する行と比較してください。

## 結果を読む

意図して発生させるUVMエラーが検査の成功条件になる場合もあり、宣言した観測と終了条件で判定する方法は[Q7](faq.ja.md#q7-なぜuvmの全メッセージを比較せずut行だけを比べるのですか)で説明しています。

シミュレーション用のケースでは、実行スクリプト（runner）が`UT: `で始まる行を順序どおり`.expected`ファイルと比較し、指定した終了コードや診断も確認します。ログ全体が期待出力ではありません。[観測する出力](testing.ja.md#何を観測するか)で説明しています。

`pass`は指定した検査の一致、`fail`は検査条件の相違、`known`は固定版での確認タグがないVerilatorケースの差分を記録します。`unsupported`は、実行スクリプトがkirimasimの未対応機能の診断を認識した状態です。後ろ2つは成功を表しません。[判定の定義](faq.ja.md#q5-passfailknownunsupportedはどう違いますか)を参照してください。

このリポジトリの`elaboration`ケースは、不正な設計をコンパイラが拒否することを期待し、実行時のseedは使いません。`simulation`ケースはモデルを実行します。両seedの一致だけでは、X／Zを含む4-stateへの対応を示しません。[seedとコンパイル検査の件数](faq.ja.md#q201-全2727テストを2-seedで実行しましたか)を参照してください。

`--all`ではknown差分だけでVerilatorコマンドを失敗にしないため、終了コードと個々の判定を併せて確認します。[終了コードが0になる理由](faq.ja.md#q6-knownがあるのにverilatorコマンドが成功するのはなぜですか)を説明しています。

結果JSONでは`tests`内でテストIDを探し、`status`と、記録がある場合は`reason`を読むと個別の判定を確認でき、その意味は[判定の定義](faq.ja.md#q5-passfailknownunsupportedはどう違いますか)で説明しています。

再利用した結果は、記録した入力、実行スクリプト、ライブラリの条件に対する証拠です。古いJSONを現在の結果として扱う前に、[互換な記録の合算方法](results.ja.md#記録の合算)を確認してください。

差分が出た場合は、変更前に引用した規則、期待する観測、検査系の準備を確認し、期待値の誤りが疑われる場合の報告と修正は[Q18](faq.ja.md#q18-期待値の誤りはどう報告修正しますか)の手順を使います。

## 結果JSONを開く

`configuration`は要求した設定を記録するため、`seeds`の一覧だけでは各seedの実行を示さず、Verilatorで最初の不一致が後続seedの実行を止める理由は[Q14](faq.ja.md#q14-seedを2つ変えれば決定性や4値の動作も証明できますか)で説明しています。

JSONは`--json`で保存する構造化された結果ファイルで、[スモークのコマンド](faq.ja.md#q3-まず1件だけ動かすにはどうしますか)の終了後にリポジトリのrootで次を実行すると、テストID、判定、記録がある場合は理由を一覧できます。

```sh
python3 - <<'PY'
import json
from pathlib import Path

result = json.loads(Path("out/verilator-smoke.json").read_text(encoding="utf-8"))
for test_id, record in result["tests"].items():
    print(test_id, record["status"], record.get("reason", ""), sep="\t")
PY
```

`tests`内の各項目は選択した1ケースで、IDでは`tests/`と末尾の`.sv`を省き、実際のファイルとの対応は[ファイルを辿る具体例](#1件のテストをファイルで辿る)で確認できます。

項目がなければそのケースの結果は読み取れないため、[既定の選択対象と`--all`](faq.ja.md#q4-specのみのテストも含めるにはどうしますか)を確認するか、ソースのパスを明示して再実行してから判断してください。

ファイルに保存するのは判定と要約した理由で、完全なシミュレータのログではなく、不一致の理由が出たときに宣言した観測を確認する手順は[差分を調べる](#差分を調べる)で説明しています。

## 差分を調べる

差分は調査の出発点であり、変更を提案する前に期待値をどう確認するかは[修正のガイド](faq.ja.md#q18-期待値の誤りはどう報告修正しますか)で説明しています。

1. 結果JSONの`tests`内で該当ケースを探して`status`と、記録がある場合は`reason`を読み、観測した相違と未対応機能の違いを[判定の定義](faq.ja.md#q5-passfailknownunsupportedはどう違いますか)で確認します。
2. テストIDを`tests/`以下のパスとして末尾に`.sv`を付け、`:type:`、`:lrm:`、`:expected_stdout:`または`:expected_stderr_regex:`を読むと、runtimeとcompiler拒否で適用する検査を[メタデータのガイド](testing.ja.md#メタデータ)と照合できます。
3. 通常・HDL・command-lineのrunnerは供給する実装が異なるため、コマンドを再実行する前に記録したライブラリとrunnerを確認し、条件の違いを[実行環境の説明](testing.ja.md#uvmライブラリ)で調べます。
4. runtimeの差分では、選択した`UT: `行を順序も含めて指定の期待値ファイルと比べ、終了・診断の条件も確認し、ログ全体を比較しない理由を[観測の規則](testing.ja.md#何を観測するか)で確認します。
5. 報告や修正案にはテストのパス、スイートのコミット、ツールの版、コマンド、引用した条項に基づく期待動作を記録し、自作の再現例と受け入れる資料を[報告のガイド](provenance.ja.md#issueの投稿方針とフォーム)で確認します。

ビルド失敗にはruntimeの観測がなく、不正設計が受理された場合もモデルを実行せずcompiler拒否の検査が失敗し、後者の判定は[Q199](faq.ja.md#q199-compile拒否を一致に数える理由は)で説明しています。

## 1件のテストをファイルで辿る

結果IDはソース、UVMクラスは実行対象、要求IDは検査する義務を示し、以下の例で使う識別子の役割の違いは[対応付けのガイド](requirements.ja.md#引用要求実行の証拠)で確認できます。

スモークテストの結果ID `u09/test_common_phases_run_in_order`から[ソース](../tests/u09/test_common_phases_run_in_order.sv)を開くと、最初のUVM引用は9.8.1であり、[配置の規則](testing.ja.md#ディレクトリ構成)に従って`u09`にあることが分かります。

このソースでは`test_common_phases_run_in_order`は`initial`から`run_test()`を呼ぶSystemVerilogのmodule、`+UVM_TESTNAME=t`は登録済みUVMクラス`t`の選択であり、両者の指定は[メタデータのガイド](testing.ja.md#メタデータ)で区別できます。

ヘッダーの`:expected_stdout:`が指す[期待出力ファイル](../tests/u09/test_common_phases_run_in_order.expected)では`UT: connect env`が`UT: connect test`に先行し、これはchildとparentのcallbackが出す観測で、全列をrunnerが比較する方法は[観測の規則](testing.ja.md#何を観測するか)で説明しています。

[要求台帳](../coverage/requirements.json)で`UVM-PHASE-COMMON-ORDER`を検索すると条件、期待動作、制限、そのテストIDへの対応を確認でき、手元の結果JSONにある実測statusとの違いは[対応付けのガイド](requirements.ja.md#引用要求実行の証拠)で説明しています。

## 対応状況と進捗を読む

テスト、規格の識別子、要求案は異なる計数単位です。M1〜M4は開発段階の名前で、後の段階を始めても前の段階の完了にはなりません。[READMEの現在件数](../README.ja.md#現在の実行結果)と[計数単位の説明](requirements.ja.md#計数単位と対象範囲の案)を併せて読んでください。

`unassessed`は識別子に要求分解や明示分類が未記録、`partial`は要求分解が一部、`assessed`は根拠のある構造／文脈の分類を記録した状態です。構造はAPIをまとめる見出し、文脈は他の要求に関連する説明を扱います。いずれも単独で全動作の検査完了を認定しません。[棚卸しの状態](requirements.ja.md#レビュー用の未整理項目とroot別集計)を参照してください。

要求への対応がないテスト0件は、全テストに明示的な対応付けがあるという意味です。全ての必要な動作にテストがあること、全テストの成功、対象範囲の承認を意味しません。[未対応テスト0の説明](faq.ja.md#q128-未対応テスト0件ならm1m4は完了ですか)を参照してください。

`direct`の対応付けは記述した義務を直接検査し、`control`の対応付けは異なる前提の評価を助けます。補助条件の成功で元の義務を成功扱いにせず、`ai`レビューの表示は人のレビューを記録しません。[要求と観測の対応付け](requirements.ja.md#引用要求実行の証拠)で説明しています。

Checkバッジは自動検査の実行状態を示し、実行結果の表には個別の測定条件があります。比較する前に[CIの範囲](results.ja.md#継続的インテグレーション)を確認してください。

## テストの変更や報告の前に

差分への対応でテストを変える前に、規格条項から期待値を導きます。テスト本体、補助ファイル、期待値の変更には、新しい入力の識別情報と互換な測定が必要なので、[対応付けの更新手順](requirements.ja.md#テストや対応付けの更新)を参照してください。

手元の規格PDFと非公開のGhost設定はcloneでは取得できず、期待値の変更やguest実行の前に必要な資料は[引継ぎ資料のファイル案内](handoff.ja.md#ファイルとローカル資料)で確認できます。

`out/`内は自分の環境で生成する資料で、新しく取得したリポジトリには存在しない場合があります。版管理した台帳と索引が維持する入力を記録しており、[ファイルと証拠の案内](handoff.ja.md#ファイルとローカル資料)で説明しています。

Issueでは[投稿方針](faq.ja.md#商用シミュレータとissueの投稿方針)に従って期待する動作と独自の再現例を記述します。そのページで、プロジェクトが受け入れる資料を説明しています。
